# Стенд: гипотезы, эксперименты, выбор решения

`bench/` — исследовательский стенд. На нём сравнивались подходы и подбиралось решение,
которое затем перенесено в ядро `metro_obstacle_core`. Сдаваемый код — ядро и ROS-нода;
стенд в работе детектора не участвует, но показывает, как решение получено: что
проверяли, что не сработало и почему выбран финальный вариант.

Подробные цифры — [docs/EXPERIMENTS.md](../docs/EXPERIMENTS.md), устройство алгоритма —
[docs/ALGORITHM.md](../docs/ALGORITHM.md). Здесь — карта файлов.

## Ход работы

1. **Данные и разметка.** Шесть записей хакатона: разметки объектов нет, реальное
   препятствие одно. Поэтому сначала сделана своя разметка: траектория поезда, эталонная ось
   пути, генератор синтетических препятствий трассировкой лучей по сетке лидара.
2. **Круги 1–3: сравнение подходов** на 5 пустых проездах (ложные тревоги) и синтетике
   (вероятность обнаружения по дальности). Выбрана геометрия: ось пути по рельсам вблизи
   и по стенам вдали, выученный профиль полотна, «чистая зона» в верху габарита,
   раздвоенные лучи, подтверждение 3 из 5 кадров.
3. **Круг 4: хрупкость.** Разбор ложных тревог по причинам, искажения установки лидара,
   синтетика без второго отражения. Итог — ограничение поправки полотна
   `delta_clip = 0.05` и прогрев модели полотна 15 кадров.
4. **Проверяющий классификатор.** Исправлена оценка скорости (в прототипе залипала на
   нуле). Геометрия со сниженными порогами отдаёт больше кандидатов, классификатор
   LightGBM (обучен на случайных формах) отсекает фон, подтверждение 3 из 5. Это основной
   режим ядра (`default`); прежний основной режим без классификатора — `geometry`. На 5
   пустых записях (модель без проверяемой записи) — 0 ложных событий против 22.9 на км у
   `geometry`.
5. **Проверка на данных заказчика.** Синтетика заказчика и новая реальная запись
   (13.2 км, около 220 файлов `.db3`). На ней ложных 0.4 события на км у `default` против
   25.7 у `geometry`. На этих данных отвергнуты расширение коридора к краю, опускание верха
   габарита вдали, дообучение на новой записи, классификатор только дальше 20 м; найдена и
   исправлена зависимость от места старта записи (плоскость полотна теперь уточняется на
   ходу с гистерезисом).

## Карта файлов

«Итог» — что стало с результатом: взято в ядро, отвергнуто (и почему), служебный скрипт
(инструмент стенда) или разовый анализ.

### Данные и разметка

| файл | что делает | этап | итог |
|---|---|---|---|
| `data.py` | Чтение bag, кэш кадров в осях x-вперёд / y-влево / z-вверх (в исходных данных «вперёд» — это −Y), кроп 230 м × ±12 м. Здесь же пути `LCT_DATA`, `LCT_CACHE` и потолок `LCT_WORKERS` | основа стенда | служебный |
| `survey.py` | Обзор каждого bag: положение лидара над полотном, сетка лучей, картинки сцен | круг 1 | разовый анализ; из него — dual return, сектор, высота лидара |
| `odom.py` | Эго-движение по облакам (KISS-ICP) и проверка его вырождения вдоль оси тоннеля | круг 1 | как оценка скорости отвергнуто: в однородном круглом тоннеле около 2 км/ч при реальных ~54 км/ч. Повороты из KISS-ICP остались только в траектории стенда (`traj.py`) |
| `profile_speed.py` | Скорость без ICP: сдвиг продольного профиля средней интенсивности стен между соседними кадрами | круг 1 | взято в ядро (оценка пройденного пути для подтверждения по кадрам). Профиль по густоте точек отвергнут: «залипает» на нуле, рисунок колец движется вместе с лидаром |
| `traj.py` | Траектория поезда для стенда: продольный шаг по профилю стен + Витерби (ограничение ускорения), поворот и боковой сдвиг из KISS-ICP | круг 1 | служебный (разметка для синтетики и эталонной оси) |
| `truth.py` | Эталонная ось пути офлайн: вблизи — будущая траектория, дальше — стены со смещением из ближней зоны | круг 1 | служебный (разметка). Как ось детектора («Oracle») отвергнута: не видит поворота лидара к пути (~1.7°), ложных 19.4% кадров против 2.6% |
| `truth_qa.py` | Картинки для визуальной проверки эталонной оси: вид сверху и сбоку с габаритом | круг 1 | служебный |
| `synth.py` | Генератор синтетических препятствий: трассировка лучей по сетке Pandar128, пятно луча, частичное попадание, объект неподвижен в мире | круги 1–4 | служебный: на нём измерено обнаружение по дальности |
| `pts_vs_range.py` | Сколько точек лидар кладёт на объект в зависимости от дальности (пресеты синтетики) | круги 1–3 | разовый анализ: предел сенсора (мелкие объекты дальше ~80 м — 2 точки и меньше) |

### Прототип и сравнение подходов

| файл | что делает | этап | итог |
|---|---|---|---|
| `detect.py` | Прототипы детектора: ось коридора (прямая, рельсы+стены, только рельсы, Калман, эталон) × модель полотна × накопление кадров; конфиги кругов 1–3 | круги 1–3 | победитель — ось рельсы+стены, профиль полотна, «чистая зона», раздвоенные лучи, подтверждение 3 из 5 — перенесён в ядро (сверка покадрово, `tests/parity.py`). Отвергнуты: только рельсы (ось 54 м), Калман по оси (держится за старую модель на стрелках), фон по лучу (24.6% кадров), сетка уверенности (обнаружение дальше 40 м почти 0), накопление точек за 3 кадра (объект размазывается), продление оси на 30 м (дальности не прибавилось, ложных в 1.5 раза больше) |
| `core_adapter.py` | Ядро `metro_obstacle_core` под интерфейс детектора стенда (конфиги `core:default`, `core:geometry`, `core:strict`, `core:soft`) | финальный прогон | служебный: цифры финала относятся ровно к сдаваемому коду |
| `evaluate.py` | Основной прогон: ложные тревоги на пустых проездах, обнаружение на синтетике, сводные таблицы | круги 1–3, финал | служебный (основная метрика) |
| `round4.py` | Четвёртый круг: детектор задаётся строкой «режим\|параметры», искажения установки (крен, поворот, тангаж, высота), синтетика без второго отражения | круг 4 | взято: `delta_clip = 0.05` (ложные 6.1% → 2.7% кадров, снята чувствительность к крену) и прогрев 15 кадров. Отвергнуто: выравнивание облака по полотну и калибровка по 10 кадрам (на переходе круглый → сдвоенный 26% кадров против 19%), `floor_fast` / EMA / `dil_k` (без эффекта), `delta_clip = 0` (теряет мелкие объекты) |
| `make_figures.py` | Графики `docs/img/` и таблицы для EXPERIMENTS.md по готовым результатам в `out/`; сам ничего не прогоняет | документация | служебный |

### Разбор ошибок

| файл | что делает | этап | итог |
|---|---|---|---|
| `funnel.py` | Воронка потерь: на каком шаге (конец оси, вне коридора, порог, правила кластера, подтверждение) ядро теряет видимый объект на дальности | круг 4 | разовый анализ |
| `fp_debug.py` | Картинки кадров с ложными тревогами на пустых bag, точки-кандидаты подсвечены | круги 1–3 | разовый анализ |
| `clean_zone.py` | Насколько пуст верх габарита (выше 0.5 м над нормой) на пустых проездах, по дальности | круг 2 | обоснование «чистой зоны» (пусто в ≥ 99% кадров до 60 м) — взята в ядро: там достаточно 2 точек, кабель находится в 2–3 раза чаще без роста ложных |
| `depth_layer.py` | Слой «скачки глубины» (картинка дальностей кольцо × азимут) как независимое подтверждение дальних кандидатов | круг 4 | отвергнут: 7–10 кандидатов на кадр на пустом тоннеле, дальше ~100 м упирается в ту же ось коридора |

### Проверяющий классификатор

| файл | что делает | этап | итог |
|---|---|---|---|
| `verifier.py` | Сбор кандидатов ядра в мягком режиме без подтверждения (пустые записи — метка 0, объект синтетики — 1; `collect_rand` — случайные формы), обучение LightGBM с отложенной записью | классификатор | взято в ядро: признаки — только из выхода ядра, модель на случайных формах |
| `verifier_e2e.py` | Честная сквозная проверка: для каждой записи модель без неё, порог — по пустым записям обучающей части; геометрия с пониженными порогами + классификатор + 3 из 5; отложенная форма (модель без человека → человек), наивная вставка | классификатор | взято: это схема основного режима `default` (на 5 пустых проездах — 0 ложных) |
| `verifier_nd.py` | Дообучение классификатора на отрицательных примерах новой записи (4 отрезка, модель для отрезка — без него; модель `rand3`) | проверка на данных заказчика | отвергнуто: ложные почти те же, дальность по мелочи хуже (2×0.2 м заказчика — с 32 м вместо 50) |

### Проверка на данных заказчика

| файл | что делает | этап | итог |
|---|---|---|---|
| `customer.py` | Прогон вариантов детектора на синтетике заказчика (`cloud_with_fake_obj`, облако без ring и timestamp, чтение как в ноде); группировка детекций в места по пройденному пути; `train` — полная модель классификатора по всем пустым записям. Здесь же набор вариантов для `newdata`/`starts` | проверка на данных заказчика | служебный. Варианты `low+ver2` (расширение коридора к краю `margin0=0`, опускание верха габарита вдали `top_k`) и `core_default_s20` (классификатор только дальше 20 м, `verify_smin=20`) — отвергнуты: первые два дают рост ложных на реальных данных; `verify_smin=20` на новой записи дал 5.7 события/км против 2.1 при тех же точках старта (прогон отрезками с 6 точками старта при прежней калибровке по первому кадру, один из стартов неудачный; финальный `default` по всей записи с 12 стартами — 0.4; классификатор нужен и вблизи), а выиграл лишь висящий стержень на 12 м |
| `newdata.py` | Ложные тревоги на новой реальной записи (одна длинная запись, ~220 кусков `.db3`, чтение через sqlite); запись режется на отрезки — каждый как новый старт ноды | проверка на данных заказчика | основание выбора режима: `default` — 0.4 события на км на 13.2 км против 25.7 у `geometry` |
| `starts.py` | Старт записи с разных файлов: тревоги на общем участке и итоговая плоскость полотна | проверка на данных заказчика | нашёл зависимость от места старта (старт в неудачном месте давал наклон плоскости 4.4° и 10 ложных кадров на общем участке); в ядро взято уточнение плоскости на ходу — медиана накопленных оценок (`plane_every`) с гистерезисом 1° / 5 см (`plane_tol_deg`, `plane_tol_d`): без гистерезиса на коротких записях лишние ложные (0.5 события на км) |
| `calib_stress.sh` | Проверка уточнения плоскости: `starts` с 4 стартов и `newdata` по всей записи (12 отрезков), до (`core_default_plane0` — плоскость по первому кадру) и после (`core_default`) | проверка на данных заказчика | служебный (регрессия для уточнения плоскости) |

## Запуск

Из корня репозитория, в окружении с ядром и зависимостями стенда (`.venv`):
`python -m bench.<скрипт>`. Результаты пишутся в `out/` (в репозиторий не входит).

**Пути к данным** — через переменные окружения, иначе берутся значения по умолчанию
(пути по умолчанию — с машины разработчика, задайте свои):

| переменная | что | по умолчанию |
|---|---|---|
| `LCT_DATA` | каталог с записями хакатона | `~/Downloads/archive/extracted/for_hackathon` |
| `LCT_CACHE` | кэш кадров и траекторий | `~/Downloads/archive/cache` |
| `LCT_CUSTOMER` | синтетика заказчика (`cloud_with_fake_obj`) | `~/Downloads/archive/customer/cloud_with_fake_obj` |
| `LCT_WORKERS` | число параллельных процессов стенда | 70% ядер машины |

Каталог новой записи (`new_data`) передаётся аргументом (в `calib_stress.sh` — обязательным).

**Нагрузка.** Прогоны `evaluate`, `round4`, `verifier`, `verifier_e2e`, `newdata`
параллельны и занимают `LCT_WORKERS` процессов. Не подчиняются `LCT_WORKERS`:
`customer run` — процесс на каждый вариант, `starts` — на каждую пару «старт × вариант»
(в примере ниже 8), `verifier_nd` — 4 процесса (по отрезку записи). Прогоны на полных
данных долгие; на ноутбуке стоит задать `LCT_WORKERS` меньше числа ядер, сузить список
вариантов и держать numpy/numba в один поток:
`NUMBA_NUM_THREADS=1 OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1`.

```bash
# разметка (один раз): кэш кадров, KISS-ICP (повороты), траектория
python -m bench.data
python -m bench.odom
python -m bench.traj

# сравнение подходов и финальный прогон ядра
python -m bench.evaluate empty "core:geometry,core:strict,core:soft"   # ложные тревоги
python -m bench.evaluate synth "core:geometry,core:strict,core:soft"   # синтетика
python -m bench.evaluate report
python -m bench.round4 empty && python -m bench.round4 synth && python -m bench.round4 report
python -m bench.make_figures                                          # графики и таблицы

# проверяющий классификатор
python -m bench.verifier collect_rand                    # кандидаты на случайных формах
LCT_VTAG=rand python -m bench.verifier_e2e models_rand   # модели «без проверяемой записи»
LCT_VTAG=rand python -m bench.verifier_e2e run rand      # geometry против default, честно
python -m bench.customer train rand                      # полная модель (как в пакете)

# данные заказчика
python -m bench.customer run - geometry,core_default   # синтетика заказчика (LCT_CUSTOMER)
python -m bench.customer report
python -m bench.newdata run <каталог new_data> core_default,geometry
python -m bench.newdata report
python -m bench.starts <каталог new_data> 111,130,145,148 core_default,core_default_plane0 148-158  # файлы 148–157 включительно
bash bench/calib_stress.sh <каталог new_data>

# просмотр в Lichtblick / Foxglove
NUMBA_NUM_THREADS=1 OMP_NUM_THREADS=1 python -m bench.to_mcap \
    /path/to/bags/doubleT_obstacle --max-frames 100
```
